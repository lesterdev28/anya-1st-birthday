Generating the art on your own machine

Seventeen assets, in the order they should be made, with every setting and the exact filename each one needs. Generate the first, stop, and send it over.

Why this exists

The tooling in the repo talks to the Higgsfield API, which bills its own credit balance — a separate balance from a Higgsfield web subscription. That one is empty, and topping it up would mean paying twice for what the subscription already covers. This run-sheet does the same job from a machine signed in to the subscription instead.

Every prompt here is the exact string the tooling would have sent, composed from the canon in tools/art-direction.ts. The repetition between them is deliberate: it is what keeps the castle the same castle across all seventeen. Don’t reword them. If one comes back wrong, the canon gets fixed and these regenerate.

1 · Install and sign in

In PowerShell, on the machine with your Higgsfield login:

npm install -g @higgsfield/cli
higgsfield auth login

auth login opens your browser and waits for you to approve it there. It has to be the browser on the same machine as the CLI — which is exactly why this part could never be done from our end.

Then check the model names on your account, since the catalogue moves:

higgsfield model list

These commands use for images and for video. If model list shows a newer Seedance, use that one and keep every other setting the same.

2 · The run

Each command waits for the generation to finish and then prints a result URL. The CLI doesn’t save the file for you — download it from that URL and put it at the path shown on the card. The filename matters: the site looks each asset up by that exact name, and anything it can’t find quietly falls back to the painted version.

Start with number one and stop there. The mobile hero sets the look, and the other sixteen are judged against it. Send it over before running the rest — if something needs to change, it is far cheaper to change it once than seventeen times.

3 · Where everything goes

Keep the -raw on the two clips. It marks them as the untouched download, so the compression step never overwrites your original.

4 · Once the files are in

From the repo:

cd tools
npm install
npm run optimize

That builds the WebP and AVIF sizes the site actually loads, makes a blurred placeholder for each, and rewrites the manifest that tells the site which assets exist. Your originals are left alone. Commit the originals, the optimized/ folders and the manifest together.

The two clips need ffmpeg, which the optimize step doesn’t do. The three commands per clip are in the repo’s README.md under Videos — an MP4, a WebM and a poster frame. The poster isn’t optional: it is what a guest sees while the clip loads, and what stays on screen if the clip never plays at all.

5 · CLI or the web app

The web app is signed in to the same subscription, and the site doesn’t care which tool made a file. Paste the same prompt, set the same aspect ratio, save it under the same name.
